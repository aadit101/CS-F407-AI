## 3. Prompt used (Task 2)

*"I want to implement a simple planning agent in Python. Represent a state as a set of logical propositions. Each action should contain: a name; positive preconditions; negative preconditions; positive effects; negative effects. An action is applicable if all of its preconditions are satisfied by the current state. When an action is applied: (1) remove its negative effects from the state; (2) add its positive effects to the state. Use breadth-first search to find a sequence of actions that achieves a specified goal. The program should also: detect when no plan exists; print the resulting sequence of actions; print the states reached after each action. Explain the implementation and identify any assumptions you make."*

Follow-ups: "add a function that replays a plan and checks every precondition"; "add a flag that switches precondition checking off".

## 4. Generated program

See `planner.py` / the notebook. Assumptions: states are `frozenset`s of propositions (closed-world); effects applied as delete-then-add; BFS returns a plan with the fewest actions.

| Idea | Code |
|---|---|
| Preconditions | `is_applicable`: `pos_pre <= state and neg_pre.isdisjoint(state)` |
| Effects | `apply_action`: `(state - neg_eff) \| pos_eff` |
| Goal | `goal <= state` in `bfs_plan` |
| BFS | FIFO `deque` frontier + `parent` dict (also the visited set) |

**Generated by the LLM:** `Action`, `bfs_plan`, `is_applicable`, `apply_action`, action constructors. **Added/modified:** the `check_preconditions` switch, `verify_plan`, `reachable_states`, and the assert-based tests.

## 6. "Think About It" and Task 4 answers

**Logic and search.**
```
Current state
  ↓
Check action preconditions        (logic: S ⊨ Pre(a)?)
  ↓
If yes → applicable; if no → discard the action   (the "?" box)
  ↓
Generate successor state          (logic: S' = (S − neg effects) ∪ pos effects)
  ↓
Search over alternatives          (search: queue S' unless already visited)
  ↓
Goal?                             (logic: S' ⊨ G ? stop : next state from the queue)
```
Logic determines what is *possible* (which actions apply, what they change, whether the goal holds); search determines what to *try* (which states to expand next, avoiding repeats, recording how each was reached). Logic without search knows the rules but has no strategy; search without logic tries impossible actions. Planning is the same graph search as the previous module, except the graph is generated from logical action descriptions.

## 7. Task 5 – Can the LLM verify its own plan?

The LLM's step-by-step explanation was compared with the states computed by the program: all 5 states matched. **Trust (b), the independently executed transitions.** The explanation is generated text that is plausible whether or not it is right, while the executed transitions are deterministic and re-checkable (the sheet's own example sequence shows how a plausible-looking plan fails when preconditions are checked). Caveat: the checker only verifies against the action model I wrote, so the model itself needs human review. *A generated explanation is not an independent verification.*

## 8. Reflection questions

1. **Why specify preconditions/effects first?** They *are* the definition of correct behaviour. Without them the LLM fills gaps with plausible assumptions, and there is nothing concrete to test against.
2. **Error without precondition checks:** the buggy planner "solved" the problem in one step, `Drop(Package,C)`, without being at C or holding the package, leaving the package in two places.
3. **Why does "looks reasonable" ≠ valid?** Validity depends on each action's preconditions in the state where it is executed. The sheet's example reads well but fails at `PickUp(Package,B)`.
4. **What the LLM contributed:** the initial BFS/STRIPS implementation, structure, explanations and test ideas.
5. **What I verified independently:** the plan step by step, correct failure on impossible problems, robot-at-C ≠ package-at-C, that precondition checking prevents bogus plans, and that the action definitions match the sheet.
6. **Where logical reasoning is used:** applicability (`S ⊨ Pre(a)`), computing successors from effects, the goal test `S ⊨ G`, the plan checker, and Prolog's rules.
7. **Planning and search:** planning is search over a state space defined by actions: states are nodes, applicable actions are edges, and BFS is the same algorithm as before, with the graph generated implicitly from logical descriptions.

## 9. Optional: Prolog (Tasks 6–8)

`planner.pl`:
```prolog
connected(a,b).  connected(b,a).  connected(b,c).  connected(c,b).
can_move(X,Y)   :- connected(X,Y).
valid_move(X,Y) :- connected(X,Y).
valid_route([_]).
valid_route([X,Y|Rest]) :- valid_move(X,Y), valid_route([Y|Rest]).
wet_road.
slippery :- wet_road.
reduce_speed :- slippery.
```

| Query | Expected (run to confirm) |
|---|---|
| `can_move(a,b)` | true |
| `can_move(a,c)` | false |
| `valid_move(a,b)` / `valid_move(b,c)` | true / true |
| `valid_move(a,c)` | false |
| `valid_route([a,b,c])` / `valid_route([a,c])` | true / false |
| `reduce_speed` | true |

- **6(a)** `can_move(X,Y) :- connected(X,Y)` matches with X=a, Y=b, and `connected(a,b)` is a stored fact.
- **6(b)** No fact `connected(a,c)` exists and no rule derives it, so it is not provable; `false` means "not derivable from this KB" (negation as failure, closed-world), not "impossible in reality". The robot reaches c by two moves, a→b→c.
- **6(c)** The rule is `∀X∀Y (Connected(X,Y) → CanMove(X,Y))` written backwards, with `:-` meaning "if" (a Horn clause).
- **Task 7 challenge:** `valid_move(a,c)` fails, so Prolog rejects `Move(a,c)`: the warehouse knowledge does not support it. Generate (Python) → independent verification (Prolog).
- **Task 8:** to prove `reduce_speed`, Prolog needs `slippery`, which needs `wet_road`, which is a fact. Forwards: **wet_road ⇒ (wet_road → slippery) slippery ⇒ (slippery → reduce_speed) reduce_speed** (two applications of modus ponens).

**Prolog reflection.** (1) A fact is unconditional; a rule derives new facts from others. (2) A query asks whether something is derivable from the KB. (3–4) An independent verifier uses a different representation and mechanism from the generator, so it does not share the generator's errors and does not depend on how convincing the LLM's output looked. Its limits: it is only as good as its facts and rules, and negation as failure ≠ classical negation.

## 10. Final reflection (summary)
The LLM produced a working planner quickly, but only testing showed *why* it works: with precondition checking switched off it returns a confident, invalid one-step plan, and even the lab sheet's example plan was invalid. Understand → Specify → Generate → Execute → Verify.
